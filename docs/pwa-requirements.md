## 0. 产品定位与三条总原则

**薄肌计划**：把「记录 → 统计 → 判断」闭环装进口袋的个人减脂增肌工具，替代当前依赖 Codex 会话的工作方式。

三条总原则贯穿全文，冲突时以本节为准：

| 编号 | 原则 | 含义 |
| --- | --- | --- |
| P-01 | **本地优先** | 记录、食物库、报告、模型配置全部存在用户设备的本地数据库（IndexedDB）。产品没有自建后端，不收集、不代管用户数据。 |
| P-02 | **强依赖大模型，但凭据由用户自备** | 营养查询、报告撰写、推荐等「知识型 / 表达型」任务由大模型完成；调用地址（URL）与 token 由用户自行配置，应用不代配、不代管、不代付、不内置任何公共密钥。 |
| P-03 | **模型只做判断与表达，不做算术** | 份量换算、汇总、占比、容量负荷、达标率、均线等确定性计算一律在本地完成，不交给模型，既省 token 又保证数字可复现。 |

由此推出两条能力分层，全文反复引用：

| 能力层 | 内容 | 依赖 |
| --- | --- | --- |
| **本地能力** | 记录、本地食物库换算、当日汇总、趋势、容量负荷、达标率、报告所需的全部数值聚合 | 无需网络、无需模型，永远可用 |
| **模型能力** | 未知食材的营养解析、周报 / 月报的结论与建议、训练与食谱推荐、校准建议 | 需联网 + 已完成模型配置 |

## 1. 背景与目标

### 1.1 现状

`foodAndWorkout` 工作区已经跑通一套以纯文本为唯一数据源的个人减脂增肌系统：

| 组成 | 现有形态 |
| --- | --- |
| 数据 | `records/` 每日摄入与训练、`plans/` 周计划、`reviews/` 周月复盘、`data/foods.csv` 食材营养库（114 条）、`profile.md` 长期档案、`targets.md` 目标与校准记录 |
| 规则 | `README.md` 的格式契约（字段名、列名、单位、口径）与 `AGENTS.md` 的工作约定、写入边界 |
| 计算 | `scripts/nutrition.py`：`init` / `new` / `totals` / `trend` / `tdee` / `lookup` / `check` / `week` |
| 判断 | 三套 skill：`fatloss-log`、`fatloss-plan`、`fatloss-review`，由大模型按 SOP 执行 |
| 同步 | Git 仓库 + commit & push，多端靠 clone + 安装 skill |

现状里「计算」是确定性的、可搬到客户端；「判断」依赖大模型；这次改造就是把这两件事分别内化到应用里。

### 1.2 痛点

1. **记录依赖对话**：在餐桌、健身房、超市掏出手机时无法随手记，只能等回到电脑前补记。
2. **计算依赖命令行**：换算、汇总、校验都要跑脚本，用户不该接触 `python scripts/nutrition.py ...`。
3. **判断不沉淀**：每次推荐与复盘都要重新组织上下文，结论用完即散。
4. **没有可视化**：趋势只有终端表格，看不出曲线、达标率与容量推进。
5. **没有提醒**：晨重、睡前重、周计划、周复盘全靠自觉（最近一周仅 3/7 天有记录）。
6. **跨设备成本高**：新设备要装 Git、clone、装 skill，冲突要手工合并。
7. **弱网不可用**：地铁、健身房、地下超市无网络时无法记录。
8. **隐私暴露**：体重、年龄、作息都放在一个公开仓库里。
9. **录入摩擦大**：一次记录要拆食材、查库、换算、写表、跑校验、贴汇总，六步串行。

### 1.3 产品目标

| 编号 | 目标 | 可衡量标准 |
| --- | --- | --- |
| G1 | 随手记 | 任意设备从打开到开始录入 ≤ 3 秒；单餐次录入（含换算）≤ 60 秒 |
| G2 | 自动算 | 份量→营养→当日汇总→占比→缺口提示全自动，用户不手算任何数字 |
| G3 | 看得见 | 体重、热量、蛋白、训练的进展以图表呈现 |
| G4 | 有判断 | 应用内直接回答：今天练什么 / 还差什么 / 这周怎么样 / 要不要校准 |
| G5 | 数据留在本地 | 断网可用；数据不上传；卸载前可完整导出 |
| G6 | 省 token | 模型只在必要时被调用，单次调用输入输出可控（见 M16 的预算） |
| G7 | 数据属于用户 | 数据可读、可导出、可迁移 |

### 1.4 成功指标

- 记录覆盖率：目标周内至少 6/7 天有摄入记录、每天有晨重（当前基线 3/7 天）。
- 录入耗时：单餐次中位数 ≤ 60 秒，首次录入 ≤ 120 秒。
- 离线可用率：无网时「记录 + 命中本地库的换算 + 当日汇总 + 趋势」100% 可用。
- 模型成本：单日记录场景的模型调用 ≤ 1 次、估算消耗 ≤ 1000 tokens；周报 / 月报单次 ≤ 3000 tokens（目标值，P1 用真实数据校准）。
- 模型成功率：结构化输出一次解析成功率 ≥ 95%（含一次自动重试）。
- 一致性：对同一份数据，应用的汇总、趋势、TDEE 结果与现有脚本一致。

## 2. 用户与场景

### 2.1 用户

**单一用户**（使用者本人，减脂增肌期、训练新手起步）。不做多账号、不共享、不做社交。
（2026-10-15 起不再在文档里保留使用者的个人身体数据；档案与目标由使用者在自己设备上录入。）

隐含特征：手机是主力记录设备；会在餐厅、健身房、超市、床上使用；不保证网络可用；愿意自行准备一个大模型 API（OpenAI 兼容接口）的 URL 与 token；不熟悉也不愿意操作命令行或 Git。

### 2.2 核心场景

| 场景 | 触发 | 期望 |
| --- | --- | --- |
| 首次配置模型 | 第一次打开 | 引导填 URL / token / 模型名 → 一键连通性测试 → 失败给出可操作的原因 |
| 餐桌记录 | 吃完一餐 | 30 秒内记完这一餐并看到当日进度 |
| 一句话记一餐 | 懒得逐条填表 | 直接写「中午吃了西红柿鸡蛋拌面，4 个西红柿、5 个鸡蛋、80g 干面条，油盐正常量」，应用解析成结构化条目并回显确认 |
| 拍照记一餐 | 拍了餐盘 / 包装 | 上传图片 + 一句话，应用识别食材与份量；估不准的地方直接反问 |
| 训练后一句话 | 不想逐组填 | 写「今天练了腿，深蹲 4 组 8 次 60kg，腿弯举 3 组 12 次 30kg，40 分钟，挺累」，解析成训练条目并回显 |
| 遇到没吃过的食物 | 输入库里没有的食材 | 应用问模型要一次营养数据（结构化 JSON），落库后下一次直接命中本地 |
| 健身房记录 | 做完一组 / 练完一次 | 按动作记录组次重量，看到容量负荷与肌群组数 |
| 睡前 / 晨起称重 | 上床前 / 起床后 | 记体重、睡眠、精力、酸痛 |
| 站在冰箱前 | 想做饭但不知道吃什么 | 直接得到「还差什么、做哪 1-2 样、要买什么」 |
| 到健身房门口 | 不知道练什么 | 直接得到今天的动作清单与重量 |
| 周日 / 月末 | 看周报 / 月报 | 一键生成，数值全部来自本地聚合，模型只写结论与建议 |
| 线下弱网 | 地铁 / 地下室 | 记录与查看照常可用；未命中本地库的食物先占位，联网后补全 |
| 换设备 | 新手机 / 新电脑 | 安装后用导出包导入还原全部数据 |

## 3. 范围与边界

### 3.1 产品范围内

饮食与训练录入、本地食物库与模型补全、营养换算与汇总、趋势与可视化、周报与月报、推荐与周计划、目标校准、档案维护、本地存储与数据导入导出、跨设备数据迁移、提醒、模型配置、安装与离线。

### 3.2 明确不做

| 不做 | 原因 |
| --- | --- |
| 自建后端 / 云账号体系 | P-01：数据只留在用户本地 |
| 提供、代管、内置任何大模型密钥或免费额度 | P-02：凭据由用户自备 |
| 代付 / 代理模型请求 | 同上 |
| 食材库存台账 | 已于 2026-10-12 停用；不建库存表、不问「你还有什么」 |
| 饮水记录 | 已于 2026-10-11 停用，界面不提供入口 |
| 日历 / `.ics` 提醒导出 | 已定不做（OQ-8）：提醒只保留应用内提醒与本地通知 |
| 医疗建议与诊断 | 只做记录与常识性建议，越界即提示就医 |
| 社交、排行榜、教练端、多用户 | 单用户产品 |
| 自动下单买食材 | 只给采购清单与替代方案 |
| 药品、补剂推荐 | 不在范围内 |
| 用模型做算术 | P-03：确定性计算全部本地完成 |

### 3.3 与现有工作区的关系

> **2026-10-15 仓库转型**：仓库现在只放应用本体，原本的 `records/`、`plans/`、`reviews/`、
> `profile.md`、`targets.md` 与 skills 已移出（个人数据不进仓库）。本节讲的是**格式契约**：
> 使用者在别处维护的那套 Markdown 结构仍是导入 / 导出目标，字段名、列名关键字与口径不变。

- **数据契约冻结**：`README.md` 定义的 front-matter 字段名、表格列名关键字、单位与口径是接口定义。应用的数据模型必须与之对应，保证数据可回迁到原工作区。
- **初始食物库**：应用内置一份初始食物-营养成分-热量表，由现有 `data/foods.csv`（114 条）迁移而来。
- **双入口并存**：Codex 会话里的 skill 通道继续有效；应用导出的文件必须能被原工作区脚本直接消费。
- **行为等价**：现有脚本的输出是验收基准，应用的确定性计算需与之逐项一致。

## 4. 领域规则（必须固化的口径）

来自 `README.md` / `AGENTS.md` / 各 skill 的 SOP，是产品的硬约束，任何界面与流程都不得违反。

### 4.1 数据完整性

| 编号 | 规则 |
| --- | --- |
| DR-01 | 记录是唯一事实来源，所有推荐、报告与结论从历史记录推导，不依赖记忆或模型记忆。 |
| DR-02 | 不删除、不重命名、不重写历史记录，只增量补写。 |
| DR-03 | 不臆造数据：没称就留空，不用「上次的值」补；估算必须写明假设；「假设」与「数据」不可混为一谈。 |
| DR-04 | 「未记录」不等于「0」。界面必须区分空值与真实 0（如「无记录（休息日）」）。 |
| DR-05 | 食物不在库中时要先落库并注明数值来源，不允许在记录里只填一个凭空数字。 |
| DR-06 | 模型返回的营养数据属于**估算**，必须与用户实测 / 包装标签数值区分标记；两者冲突时以用户提供的为准。 |

### 4.2 口径

| 编号 | 规则 |
| --- | --- |
| DR-07 | `weight_am_kg`（晨起排尿后、空腹）是趋势与 TDEE 的**唯一基准**；`weight_pm_kg`（睡前）只用于算夜间净流失。只称一个就只填一个，不允许互相补。 |
| DR-08 | 夜间净流失 = 当天晨重 − 前一天睡前重；它是水分与肠内容物的变化，**不是「夜间代谢」**，界面需带此说明。 |
| DR-09 | 同日「睡前 − 晨重」= 当天摄入的食物与液体净质量，可用于粗查漏记。 |
| DR-10 | 早期 `weight_kg` 为兼容字段：仅当该日无晨重时兜底，且必须标注口径不明。 |
| DR-11 | `soreness` / `energy` 为 1-5 固定口径自评，界面必须内联口径表；关节痛、单侧痛、肿热、麻木等按伤病处理并建议就医，不得塞进 1-5。 |
| DR-12 | `sleep_hours` 为实际睡着时长，不是躺床时长。 |

### 4.3 摄入与营养

| 编号 | 规则 |
| --- | --- |
| DR-13 | 摄入记录**一行 = 一个食材**；同一道菜的多个食材共用同一个「菜品/做法」值。 |
| DR-14 | `餐次` 只能是 早餐 / 午餐 / 晚餐 / 加餐。 |
| DR-15 | 做法带来的油、糖、酱料、淀粉必须单独成行，不允许藏在主料里。 |
| DR-16 | 食物库数值为每 100g / 100ml **可食部**；标注生熟的以标注为准，未标注按生重。 |
| DR-17 | 食用油按入锅量记录，不按锅底残留估算。 |
| DR-18 | 份量不明确时按常见基准估算并写明假设（鸡蛋 1 个 ≈ 50g、一碗米饭 ≈ 150g 熟饭、一勺油 ≈ 10g）。 |
| DR-19 | 汇总与占比由本地计算，用户不手算；占比列必须保留展示。 |

### 4.4 训练

| 编号 | 规则 |
| --- | --- |
| DR-20 | 训练记录**一行 = 一个动作**。 |
| DR-21 | `组x次x重量` 形如 `4x8x60kg`，自重写 `3x12x自重`；**容量负荷 = 组 × 次 × 重量（自重不计）**，是力量训练主指标。 |
| DR-22 | 有氧消耗 = `MET × 3.5 × 体重(kg) / 200 × 时长(min)`；**缺时长就留空**，不得凑数。 |
| DR-23 | 有氧看热量、力量看容量负荷与肌群组数，**两者都不冲抵热量目标**，仅用于观察活动量。 |
| DR-24 | `目标肌群` 多肌群用 `/` 分隔；`类型` 建议取值：力量 / 有氧 / 球类 / 拉伸 / 其他。 |

### 4.5 判断与输出

| 编号 | 规则 |
| --- | --- |
| DR-25 | 区分**事实**（记录里的数字）与**推断**（解释），推断必须显式标注。 |
| DR-26 | 看趋势不看单日；单日 ±1kg 是水分波动，不是脂肪。 |
| DR-27 | 样本不足就不下结论：TDEE 反推需 ≥14 天（至少 7 天）同时有晨重与完整摄入；训练不足 7 天不外推周均。必要时标注「初步估算」。 |
| DR-28 | 热量目标已包含日常活动与训练消耗，不允许把训练消耗加回目标。 |
| DR-29 | 推荐不依赖、也不询问食材库存；约束只来自档案里的调味料有无、忌口过敏、可用器材、每餐可投入时间。 |
| DR-30 | 小步校准：每次只调 ±100~150 kcal，观察 1-2 周再评估，不一次砍 500 kcal。 |
| DR-31 | 校准频率 2-4 周一次，或体重停滞 ≥10 天。 |
| DR-32 | 目标只在报告 / 校准时修改，且必须同时在「校准记录」补一行（日期 / 实测 TDEE / 调整前后 / 依据）。 |
| DR-33 | 档案记录长期事实，不因单次表现修改；正文与结构化字段冲突时以结构化字段为准，并提示把正文值同步过去。 |
| DR-34 | 输出落点固定：推荐类属「计划」，回顾类属「报告」，不混进每日记录。 |
| DR-35 | 数据不足时直说，不假装能看出趋势；不承诺具体减重数字。 |
| DR-36 | 非医疗产品：出现持续疲劳、睡眠障碍、月经异常、关节疼痛等，建议就医或咨询注册营养师，不继续加量。 |
| DR-37 | 报告必须引用本地聚合出的数值，**不得由模型自行计算或改写数字**；模型输出中出现的数字若与输入不一致，以本地数值为准并标记异常。 |

### 4.6 大模型调用规则

| 编号 | 规则 |
| --- | --- |
| DR-38 | 模型调用地址与 token 由用户配置并只存在本地；应用不得内置密钥、不得把凭据发给除用户配置地址以外的任何一方。 |
| DR-39 | 调用前先查本地：命中本地食物库或本地缓存的结果直接使用，**不重复请求模型**。 |
| DR-40 | 请求只携带完成任务所需的最小字段，不带全量历史、不带整份记录文件。 |
| DR-41 | 能合并就合并：同一餐次中多个未知食物合并为一次请求。 |
| DR-42 | 所有模型任务必须声明固定 JSON 结构，响应必须为可解析的纯 JSON；不允许自由散文。 |
| DR-43 | 模型输出必须经本地校验（结构、类型、取值范围）后才可写入数据；校验不过则重试一次，仍失败则丢弃并提示用户。 |
| DR-44 | 模型不可用时（未配置 / 断网 / 报错 / 超时）不得阻塞记录：本地能力照常工作，模型能力显示为「待补全」并排队。 |
| DR-45 | 模型结果一律标注来源（模型标识 + 时间 + 依据说明）与置信度；低置信度结果在界面上要求用户确认。 |
| DR-46 | 模型产生的任何建议都不记为事实；用户采纳后才成为目标或记录。 |
| DR-47 | **澄清优先于估算**：任何来源（自由文本、图片、模型）在无法准确得出热量、份量或训练强度时，必须向用户追问缺失信息，不得用默认值或猜测值填充。能估算的（如「一碗米饭」）要估算并写明假设；不能估算的（如「吃了顿大餐」「练了会儿」）必须先问。 |
| DR-48 | **草稿不等于事实**：由自由文本或图片解析出的内容一律先作为草稿展示，用户确认后才写入记录；未确认的草稿不参与汇总与统计。 |
| DR-49 | 图片识别结果的信息量天然弱于称重：识别出的每一条都必须标注为估算并给出置信度，份量类字段优先追问而非直接填。 |

### M8 推荐与周计划（FR-800）

> **2026-10-16 范围调整（第二版，取代上一版"本模块不做"）：分两级。**
>
> - **A 级（做，默认开）＝ 诊断型指导**：不出具体食谱 / 动作清单，只基于本地摘要指出问题与下一步
>   （例如"连续 3 天蛋白低于目标的 60%""练背容量两周没涨""睡眠 <6h 已 3 天，今天别加量"）。
>   契约见设计文档 §6.4.2 的 `coach.daily`，2026-10-16 起列为 P0。
> - **B 级（做，**默认关**的可选开关）＝ 生成式推荐**：就是下面这组 FR-801 ~ FR-808。
>   它需要档案里的**忌口 / 过敏 / 可用器材 / 每餐时间**作为安全边界，而这几个字段在 2026-10-16
>   的档案瘦身里被删掉了 —— 所以**启用 B 级之前，必须先恢复这些约束字段**（见 FR-1003 的备注），
>   否则会出现"推荐了你不能吃的东西"。这是开关默认关的原因之一。

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| FR-801 | 「今天练什么」：按固定优先级输出 | 恢复优先（48 小时内练过的肌群排除）→ 补欠账肌群 → 渐进超负荷（给具体加重 +2.5kg 或加次 +1~2）→ 器材与伤病约束（给替代动作）→ 容量（4-6 动作 / 每个 3-4 组 / 对齐每次时长）；输出动作清单 + 预计时长 + 一句话重点 |

| FR-1210 | 卸载提示 | 卸载 / 清除站点数据前提示先导出 |

### M13 大模型接入配置（FR-1300）

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| FR-1301 | 用户自行配置调用地址与 token | 必填：接口地址（URL）、token；可填：模型名、超时、随请求附带的自定义参数 |
| FR-1302 | 应用不提供默认凭据 | 不内置任何密钥、不提供公共额度、不代理请求 |
| FR-1303 | 未配置时的行为 | 应用可正常记录与查看，模型相关功能显示「未配置模型」并给出一键跳转配置的引导；不出现静默失败 |
| FR-1304 | 连通性测试 | 提供「测试连接」按钮，返回成功 / 明确错误原因（地址不可达、401、403、404、429、超时、响应非 JSON） |

| FR-1307 | 多套配置（可选） | 允许保存多组配置并切换，默认使用其中一组 |
| FR-1308 | 调用可见 | 每次模型调用记录用途、时间、模型、耗时、估算 token，可在设置中查看与清空 |
| FR-1309 | 失败可重试 | 失败自动重试一次（仅针对网络 / 限流类错误），仍失败则进入待办队列并告知用户 |

### M14 结构化输出契约与 token 控制（FR-1400）

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| FR-1401 | 每个模型任务都有固定 JSON 契约与版本号 | 至少覆盖：食物营养解析、周报、月报、**每日指导（`coach.daily`，P0）**、校准建议；训练 / 食谱推荐（B 级，默认关）按其开关状态启用 |
| FR-1402 | 响应必须是可解析的纯 JSON | 不接受散文、不接受 Markdown 包裹；解析前先剥离常见包裹 |
| FR-1403 | 本地校验 | 校验结构、字段类型、枚举取值、数值范围；越界值标记可疑 |
| FR-1404 | 一次自动重试 | 解析失败时重试一次，重试只追加「校验错误摘要」，不重发完整上下文 |
| FR-1405 | 失败即丢弃 | 两次都失败则不写入任何数据，向用户显示原始响应与失败原因 |
| FR-1406 | 请求最小化 | 只发完成任务必需的字段；禁止发送全量历史记录 |
| FR-1407 | 请求合并 | 同类任务在短时间内合并为一次请求（如一次补全多个未知食物） |
| FR-1408 | 本地优先 | 命中本地库 / 本地缓存的答案不再请求模型 |
| FR-1409 | 结果缓存 | 模型结果落库，同一输入不重复请求 |
| FR-1410 | 禁止模型算数 | 换算、求和、占比、均线、达标率、容量负荷一律本地计算，不写入模型请求 |
| FR-1411 | 报告采用「本地摘要 → 模型表达」模式 | 先本地聚合出紧凑数值摘要，模型只据此写结论与建议 |
| FR-1412 | 输出长度上限 | 每个任务声明最大输出长度，避免模型长篇输出浪费 token |
| FR-1413 | token 预算 | 单次食物解析 ≤ 400 输入 / ≤ 300 输出；一句话解析 ≤ 600 输入 / ≤ 600 输出；图片解析 ≤ 1500 输入 / ≤ 600 输出（图片 token 成本高，发送前提示）；周报 / 月报 ≤ 1500 输入 / ≤ 1200 输出；推荐 ≤ 800 输入 / ≤ 600 输出（目标值，P1 用真实调用校准） |
| FR-1414 | 用量可视化 | 设置页显示累计调用次数与估算 token 消耗 |
| FR-1415 | 单一职责 | 一个任务只做一件事，不把「查食物 + 写周报」塞进同一次调用 |
| FR-1416 | 自由文本解析任务契约化 | 「一句话记录」走独立的固定 JSON 契约（草稿条目 + 缺失信息 + 假设 + 置信度），解析结果不得直接落库 |
| FR-1417 | 图片输入的处理约束 | 上传前本地压缩与裁边；单次请求图片数量与像素上限固定；请求前提示「图片将发送给你配置的模型服务」；图片不落库，仅在确认卡片上临时展示 |

## 6. 关键流程

### 6.1 首次使用

1. 打开链接 → 安装到主屏 / 桌面 → 以「薄肌计划」之名独立启动。
2. 填档案（身体基础、目标阶段、训练水平、记录口径约定）。
3. 生成启动热量与宏量目标（本地计算），并说明「这是启动值，2-4 周后按实测校准」。
4. **配置模型**：填接口地址、token、模型名 → 测试连接 → 成功 / 失败的明确原因；可跳过，跳过则进入降级模式。
5. 加载内置食物库（114 条）；提示「不记饮水、不记库存」等口径约定。

### 6.2 记录一次正餐

1. 主屏快捷入口 → 「记一餐」。
2. 选餐次（按当前时间推断，可改）。
3. 搜索食材：命中本地库直接换算；未命中则询问是否请模型解析。
4. 若一次出现多个未知食物，合并为一次请求（DR-41）。
5. 若有煎炒 / 红烧，提示补一行油 / 糖 / 酱料。
6. 保存后立即看到：本餐合计 + 当日累计 + 差额与占比 + 缺口提示。
7. 全程无网时：命中本地库的部分照常；未命中的先占位；汇总标注为不完整。

### 6.3 生成周报 / 月报

1. 进入「报告」，选择周或月。
2. 本地先聚合出数值摘要（不调模型）：覆盖天数、摄入均值、达标率、体重均线与变化、训练天数 / 组数 / 容量、上一期结论摘要。
3. 用户可预览将要发送的内容（FR-1602）。
4. 调用模型，要求返回固定 JSON 的报告字段；本地校验后渲染。
5. 数字全部采用本地聚合值；模型文中若出现不一致的数字，以本地为准并标记异常（DR-37）。
6. 报告落库，可按周 / 月回看；未配置模型或断网时先出数值部分，结论排队待生成。

### 6.4 健身房记录一次训练

1. 进入「记训练」，选择类型（默认力量）。
2. 选目标肌群与动作（可收藏常用动作）。
3. 每动作填 `组x次x重量`；自重动作写「自重」。
4. 有氧必须填时长，否则消耗留空并提示。
5. 保存后看到本次容量负荷、本周各肌群组数进度、距上次同肌群训练的天数（全部本地计算）。

### 6.5 一天收尾

1. 睡前提醒 → 记睡前重（可跳过）。
2. 系统列出当天仍为空的字段与「待补全」条目，并给出每项的建议给法。
3. 用户逐项确认或留空；声明的「不记」字段进入不再追问名单。
4. 本地完成校验与当日汇总；若有待补全条目，联网后自动补全并回算。

### 6.6 换设备

1. 在新设备安装并打开应用。
2. 通过导出包导入还原数据。
3. 重新填一次模型配置（凭据不随导出包迁移）。
4. 校验数据完整性后继续记录。

## 9. 免责声明与安全提示（产品内必须存在）

- 本产品提供的是基于公开营养学与训练学常识的记录工具与建议，**不构成医疗建议**。
- 有基础疾病、进食障碍、孕期或伤痛的，先咨询医生或注册营养师。
- 体重变化建议控制在每周 0.5%~1% 体重以内，不长期执行极端低热量饮食。
- 热量长期明显低于目标时，主动提示肌肉流失与 TDEE 下降风险。
- 出现持续疲劳、睡眠障碍、月经异常、关节疼痛、肿热麻木、尿色变深等情况，提示就医，不继续加量。
- **模型生成的营养数据属于估算**，包装标签或用户实测值优先；不要把估算值当成精确数据。
- 模型由用户自行配置，其可用性、准确性与费用由用户与其服务提供方决定。

## 10. 边界情况与异常处理

| 情况 | 期望行为 |
| --- | --- |
| 未配置模型 | 记录与查看照常；模型功能显示「未配置」并给配置引导；不静默失败 |
| 模型地址 / token 错误 | 连通性测试给出明确原因（401 / 403 / 404 / 超时 / 非 JSON） |
| 模型返回非 JSON 或结构不符 | 剥离包裹 → 校验 → 失败则重试一次（只附错误摘要）→ 仍失败则丢弃并提示 |
| 模型限流 / 超时 | 自动重试一次；仍失败进入待办队列，不阻塞记录 |
| 模型给出的数值离谱 | 标记可疑并要求用户确认后才可写入 |
| 库中无该食材 | 引导请求模型或手工录入，必须带来源；不允许只填凭空的数字 |
| 离线时输入未知食物 | 先占位（名称 + 份量），标记「营养待补全」，联网后补全并回算 |
| 份量记不清 | 按常见基准估算并写明假设；无法确定时留空，不编 |
| 描述模糊（「吃了顿大餐」） | 先追问菜品与大致份量，不硬猜 |
| 训练缺时长 / 缺 RPE | 主动询问；答不上来就留空；缺时长则有氧消耗留空 |
| 组次重量格式非法 | 明确提示，并说明将按 1 组统计 |
| 报告样本不足 | 标注「初步估算」或拒绝给校准建议，并显示覆盖率 |
| 报告里模型自带数字 | 与本地聚合值不一致时以本地为准并标记异常 |
| 从未记录 vs 记录为 0 | 界面必须区分（如「-」vs「0」） |
| 存储空间不足 | 提前提示，并可清理缓存与调用日志（不动记录） |
| 浏览器清除站点数据 | 提前提示先导出；导出流程给出一键备份 |

## 13. 验收清单（整体）

1. 在 iOS、Android、Windows 三个平台均能安装，并以「薄肌计划」之名独立窗口运行（FR-1501 / FR-1502）。
2. 未配置模型时，记录、汇总、趋势全部可用，且模型入口给出明确引导而非报错（FR-1303）。
3. 配置模型后「测试连接」能区分成功与各类失败原因（FR-1304）。
4. 输入一个库中不存在的食物：请求一次模型 → 返回 JSON → 校验通过 → 落库 → 再次输入同名食物时不再调用模型（FR-403 / FR-404 / FR-1409）。
5. 一次录入含 3 个未知食物时只产生 1 次模型请求（FR-409 / DR-41）。
6. 断网状态下可完成「新增一餐（库内食物）→ 换算 → 保存 → 看到当日汇总与占比」；未命中食物以「待补全」占位，联网后自动补全并回算（FR-1503 / FR-1504 / FR-410）。
7. 一条饮食记录 = 一个食材，油 / 糖 / 酱料单独成行（FR-103 / DR-13 / DR-15）。
8. 只填晨重时睡前重为空；趋势与 TDEE 只使用晨重（DR-07）。
9. 容量负荷与有氧消耗本地计算正确；缺时长时消耗为空并提示（FR-203 / FR-204）。
10. 生成一次周报：数值全部来自本地聚合，模型调用输入为紧凑摘要；报告里若混入模型臆造数字，应用能发现并以本地值为准（FR-703 / FR-704 / DR-37）。
11. 模型返回的非法 JSON 会被拦截：重试一次后仍失败则丢弃并提示，且不写入任何数据（FR-1403 / FR-1405）。
12. 修改目标时同时写入一行校准记录，且单次幅度不超过 ±100~150 kcal（FR-903 / FR-904）。
13. 导出包可在另一台设备导入还原；导出包中不包含模型 token（FR-1204 / FR-1205 / FR-1305）。
14. 导出的记录文本能被原工作区脚本直接消费（FR-1206）。
15. 设置页可看到模型调用次数与估算 token 用量（FR-1414）。
16. 界面中不存在食材库存与饮水入口；已声明不再记的字段不再追问（FR-1005 / FR-1103 / 3.2）。
17. 免责声明与安全提示可在应用内找到（NFR-12 / 第 9 节）。
18. 输入「中午吃了西红柿鸡蛋拌面，4 个西红柿、5 个鸡蛋、80g 干面条，油盐正常量」：解析出 3 条以上食材条目、保留原文、追问「80g 是干重还是熟重」「油盐用量」，确认后才落库（FR-110 / FR-112 / FR-113 / DR-47）。
19. 输入「今天练了腿，深蹲 4 组 8 次 60kg，练了 40 分钟」：解析出动作与组次重量，追问 RPE，缺项不填（FR-208 / FR-209）。
20. 上传一张食物图片 + 一句话：识别结果以草稿形式给出、每条标为估算并带置信度，份量类字段优先追问；图片不被保存到本地库（FR-111 / FR-1417 / DR-49）。

## 14. 本地数据实体（需求级）

以下实体必须持久化在本地数据库（IndexedDB）中，字段口径与既有契约对应。命名与内部结构由实现决定。

| 实体 | 关键内容 |
| --- | --- |
| 每日记录 | 日期、周几、晨重、睡前重、睡眠时长、精力、酸痛、摄入条目列表、训练条目列表、状态与备注、待办、汇总快照 |
| 摄入条目 | 餐次、菜品/做法、食材引用、份量、热量、蛋白、脂肪、碳水、纤维、钠、是否待补全 |
| 训练条目 | 时间、类型、时长、RPE、目标肌群、动作、组x次x重量、估算消耗、容量负荷 |
| 食物条目 | 名称、分类、计量单位、热量、蛋白、脂肪、碳水、纤维、钠、生熟说明、来源类型（内置 / 模型 / 手工）、来源说明、置信度、创建时间、是否停用 |
| 报告 | 类型（周 / 月）、期间起止、本地聚合数值、模型结论（结构化字段）、是否人工编辑、生成时间、模型标识、版本 |
| 目标 | 热量与宏量目标、训练策略、每肌群组数下限、目标体重与速率、上次校准时间 |
| 校准记录 | 日期、实测 TDEE、调整前后、依据 |
| 档案 | 身体基础、阶段目标、训练水平、作息、记录口径约定（2026-10-16 调整：与推荐相关的字段已移除） |
| 模型配置 | 接口地址、token、模型名、超时与参数、是否启用、连通性测试结果。**不参与导出** |
| 调用日志 | 用途、时间、模型标识、耗时、估算 token、成功 / 失败原因。可清空 |
| 待办队列 | 待补全的食物、待生成的报告、失败的调用与重试次数 |
| 设置 | 单位、周起始日、外观、提醒、不再追问字段 |
| 备份快照 | 快照时间、范围、内容摘要（用于回滚单日记录） |

## 15. 术语表

| 术语 | 含义 |
| --- | --- |
| 薄肌计划 | 本产品名称 |
| 本地能力 | 不依赖网络与模型的确定性功能，见第 0 节 |
| 模型能力 | 需要用户配置的大模型才能完成的功能，见第 0 节 |
| 事实来源 | 每日记录，所有推导的起点 |
| 晨重 / 睡前重 | 晨起排尿后空腹体重（趋势与 TDEE 唯一基准）/ 睡前体重（仅算夜间净流失） |
| 夜间净流失 | 当天晨重 − 前一天睡前重；反映水分与肠内容物，不是「夜间代谢」 |
| 容量负荷 | 组 × 次 × 重量，自重不计；力量训练主指标 |
| 达标率 | 热量按 ±10%、蛋白按不低于目标统计的达标天数占比 |
| 缺口 | 当日摄入与目标的差额 |
| 校准 | 依据实测体重变化反推真实 TDEE 并调整目标，必须留痕 |
| 覆盖率 | 一段区间内有记录的天数占比，决定结论可信度 |
| 结构化输出契约 | 每个模型任务的固定 JSON 结构与版本，见 M14 |
| 待补全 | 记录已保存但营养数据尚未由模型补全的条目 |
| 待生成 | 数值部分已就绪、等待模型撰写结论的报告 |
| 降级模式 | 未配置模型或不可用时的运行状态：本地能力全开，模型能力排队 |
